# R5 — How should this build actually go faster?

**Status: ANSWERED 2026-08-22.** Written 2026-08-22 for a Deep Research pass. Paste the whole file. The answer is filed at `docs/research/answers/R5-answer-build-velocity.md`.

Every number below is measured, and the measurement method is stated so you can distrust it
properly. Where something is a judgement rather than a measurement, it says so.

---

## What is being built

A **factory for agent teams whose output can be certified rather than believed**. The estate it
serves has twice shipped mechanisms that *acted* without anything measuring whether the action
worked: a pipeline agent that ran 81 days producing 233 diagnoses and **zero fixes**, and an
automated loop that ran 965 times, recorded its own success rate at 1.6%, and never adjusted.
Neither was stopped by a monitor, because in both cases the thing being counted was **activity**,
and activity was exactly what they were good at.

So the central artifact is not an agent. It is a **GreenContract**: 12 assertions (A1–A12) a
connector migration must satisfy end to end, with four verdicts that are never collapsed —
`PASS` / `FAIL` / `UNMEASURABLE` / `NOT_RUN`. `UNMEASURABLE` is not a pass and exits non-zero. The
distinction between "it is broken" and "I could not look" is the whole point.

## The build process, described honestly

**1. The work list is the gate list.** `python -m factory.readiness` runs 30 probes, each measuring
a fact from a file at the moment you run it and naming the path it measured from. Every gate that
fails **is** a task; a gate that passes stops being one. There is no second backlog to keep in
sync, so the board cannot describe work nobody measures, or omit work somebody does. The only
hand-authored part is which gate must precede which, and a stale dependency edge fails on import.

**2. Everything on the readout is generated.** Four surfaces show the same measurement: the CLI, a
local server that re-measures per request, a section of an HTML readout, and a published artifact.
Three of the four are generated by scripts with `--check` modes.

**3. Evidence files, not claims.** Each significant piece of work leaves
`docs/evidence/<topic>-<date>.md` containing the commands, the outputs, and a **"what this does not
buy"** section. Some gates are satisfied by the *existence* of such a file.

**4. Boot prompts as the session boundary.** Context is finite, so each session writes
`boot-prompts/<workstream>-<date>.md` for the next: current state, a `next:` line, an explicit
NOT-done list, and gotchas earned. Sessions are effectively one-shot workers with a written handoff.

**5. A findings ledger between parallel lanes.** `docs/findings.md` holds only **corrected
premises** — "what another lane would otherwise believe, and what is actually true, and the
discriminating test". Closing a lane with `NOTHING TO REPORT` is itself an entry.

**6. Mutation testing on controls.** A control that has never been watched refusing something is
treated as decoration. New guards are broken on purpose to confirm the test catches it.

## The measured problem

Velocity is read out of the readout's own git history — every commit carries a generated
`n of N gates pass` headline and a commit date, so progress is already an append-only log.

```
window        2026-08-21 18:26 -> 2026-08-22 00:51   (6.4h, 12 snapshots)
gates passed  1  -> 9     (+8,  1.25/h)
gate set      13 -> 30    (+17, 2.65/h)
REMAINING     12 -> 21    (+1.40/h)
```

⭐ **The denominator is growing more than twice as fast as the numerator.** Measuring the system is
what reveals what is broken in it, so discovery outpaces completion. The tooling refuses to emit a
completion date for this reason and names its criterion (the total holding still for 24h). Nobody
has set a target date, so "ahead or behind" reports NOT-SET rather than inventing a baseline.

**Other measured facts about the process itself:**

- **Serial, not parallel.** One session did all of the above. Five parallel lanes now exist,
  grouped by *file locality* rather than dependency order — 16 of 30 gates have no unmet dependency,
  but two sessions editing the same file simply conflict. **Zero lanes have been run in parallel.**
- **The verification tax is large and possibly load-bearing.** In one session, three of the
  instruments built produced **confident false results**: a render probe measuring across two SVGs
  and reporting "119 marks, min gap −201px"; a text-collision check firing on a wrapped inline
  element whose bounding box is the union of its line boxes; a drift test whose HTML escaping
  differed from the generator's, reporting a gate missing from a page it was on. All three were
  caught by checking the finding against the artefact before reporting it. Roughly a third of
  elapsed time went on verifying instruments rather than building.
- **Surfaces drift silently.** The published readout said `3 of 23` while the repo was at `9 of 30`.
  A drift guard existed and had never been run. It is now in the test suite.
- **A six-session dependency was never worth it.** A browser automation tool refused to connect for
  six sessions running, blocking all visual verification; five defects shipped in the meantime.
  Replacing it took under an hour once someone tried a different route.
- **The thing everyone assumes exists, does not.** "Team one" is a specification with a version
  hash and no executor — `grep` finds exactly one caller of its loader: a test.

## The questions

**1. Is the growing denominator a discovery success or a definition failure?** The gate set went
13 → 30 in 6.4h. Two readings: (a) correct early-programme behaviour — you cannot enumerate the
work until you measure the system; (b) a scope-control failure dressed up as rigour. **What
evidence distinguishes them?** Is there a principled point at which a measurement-derived backlog
should be frozen, and what is the failure mode of freezing too early versus too late?

**2. What is the real speed-up from parallel agent sessions on one codebase, and what is the
coordination cost?** We have five lanes and have never run two at once. The constraint we
identified is file locality, not dependencies. **Is that the right constraint?** What does the
evidence say about parallel LLM-agent sessions on a shared repository — merge conflict rates,
duplicated work, contradictory premises — and what coordination artifacts actually pay for
themselves? Does the findings-ledger idea have a name and a track record?

**3. What is the correct ratio of verification to construction here?** Three false instrument
results in one session, all caught manually. **Is that a sign the verification discipline is
working, or that the instruments are too ad-hoc?** Is there a cheaper way to get the same
protection — property-based testing, differential testing against a second implementation,
something else? Where is the point of diminishing returns?

**4. Is "generate every surface" the right answer to drift, or is there a better pattern?** We now
have four surfaces and three generators with `--check` modes wired into CI-equivalent tests. That
is a lot of machinery for one readout. **What do teams that solved this actually do?**

**5. Given team one is a spec with no executor, what is the fastest credible path to a running
team?** Two options: build a runner in the factory repo, or drive the existing bespoke 18-stage
orchestrator (which has agent stages, no attempt cap, and has not run since 2026-05-28). **Which
gets to a certifiable end-to-end run sooner, and what is the minimum safe set of controls before
an agent loop is allowed to dispatch cloud containers?** Note: an uncapped restart loop previously
consumed an entire 10-core cloud quota.

**6. Is the session/boot-prompt model the right unit of work?** Each session is a one-shot worker
with a written handoff, and context exhaustion is a hard boundary. **What practices exist for
long-running multi-session agent programmes** — what belongs in a handoff, what should be
re-derived, and how do you stop a handoff becoming a second source of truth that drifts?

## What a useful answer looks like

Recommendations with a stated basis, ranked by expected effect on **time to one certifiable
end-to-end run** — not general software-productivity advice. Where you cite a practice, say whether
it was observed in a comparable setting (LLM agents, multi-session, one repo) or is being
extrapolated from human teams; those are different claims and we will treat them differently.

Say explicitly which of the six questions you could **not** find good evidence for. A confident
answer to all six would be less useful than four solid ones and two honest gaps.

## Method note

The estate's own rule, applied to its own research: *an object named by a ticket, boot prompt or
handoff is a hypothesis, not a finding — walk the route yourself before adopting it.* An earlier
research pass here named a component as the cause of a defect; it was wrong, the claim was carried
into a second research question before anyone checked, and verifying took one grep. Assume the same
about anything in this document you can check.
