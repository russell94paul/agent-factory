# Executive Summary

We recommend **adopting _switchboard_ as the substrate**, extending it sparingly for our lane/claim/gate concepts, rather than building a new system. Switchboard already implements most of the needed features (session discovery, attach/resume, notifications, cost tracking, etc.), and only lacks a few domain-specific hooks (e.g. understanding our “gates” or leveraging the existing `sessions/*.json` registry). Building from scratch would be far more work, and merely using our rudimentary scripts would leave serious gaps (identity confusion, no human alerting, etc.). Our first change should be to get switchboard running on Windows and connect it to our transcript directory, then refine naming and notification to fix the current blind spots.

The rest of this report analyzes switchboard’s actual behavior (based on its source code), compares it to our current tracker and an ideal manager (in a table), and covers the broader substrate topics: identity/liveness, human alerting of blocked agents, cost signals, productivity features, and out-of-scope/forbidden suggestions.

# 2. Switchboard (from source) – Real Capabilities 

We studied the actual code of [doctly/switchboard](https://github.com/doctly/switchboard) (v ~Feb 2026). Everything in its README that isn’t in the code is “MARKETED” hype – we rely only on the code (`OBSERVED`) and our measurements (`OBSERVED`). Below we answer the eight questions from §2.1:

- **Attach vs. spawn.** Switchboard never *attaches* to an arbitrary running process; it only re-uses (“reattaches”) PTYs that *it itself spawned*. In the `open-terminal` handler, the code checks `if (activeSessions.has(sessionId))` and only then replays buffered output into the UI. If no tracked PTY exists, it **always spawns a new CLAUDE CLI process** (with `--resume` or `--fork-session` flags as needed). In other words, if an agent is running outside Switchboard, Switchboard will treat that session as “not running” and will spawn a second process with the same session ID. There is no external liveness check or OS-level attach; Switchboard trusts only its `activeSessions` map. (→ *OBSERVED* from [40]–[41].)

- **Session discovery.** Switchboard scans the transcript directory, not the `~/.claude/sessions/` registry. It launches a worker (`scan-projects.js`) that recursively reads `~/.claude/projects/*/*.jsonl` to enumerate sessions. It builds an SQLite cache of session metadata (id, folder, title, summary, etc.) based on those JSONL files. It does **not** read `~/.claude/sessions/*.json` or consult the OS process table. Session liveness is inferred indirectly: if Switchboard itself started a session, it knows via `activeSessions`. Otherwise a session is presumed finished (or “unknown”) unless the transcript file is growing. To keep the cache fresh, Switchboard uses `fs.watch` on the projects dir: when a JSONL file changes or is added, it calls `refreshFolder` (re-reading that folder) and updates the DB. There is no explicit “age” tag shown in the UI for cached data, but at least file changes trigger an immediate refresh. (→ *OBSERVED*, [44], [46].)

- **“Needs attention” signals.** Switchboard does not use any `needs`/`status` flags from a registry (none of its code inspects `kind:bg` or `jobId` or `needs`). Instead, it decodes terminal ANSI sequences to detect busy/idle and notifications. It listens for OSC 0 title-changes to detect whether the CLI is *busy* or *idle* (sending `cli-busy-state` to the UI) and for OSC 9 sequences (bell-style notifications) as general alerts. In practice this means: when the Claude CLI prints an iTerm2 “attention” sequence (for example, the permission question prompt), Switchboard captures it and emits a `terminal-notification` event to the UI. The UI can then badge or highlight that session. So user questions (permissions, yes/no prompts, etc.) are surfaced via those OSC notifications. There is no special `needs` field read from disk; it’s entirely driven by the CLI’s own bell/OSC output. (→ *OBSERVED*, [48].)

- **SQLite cache staleness.** Switchboard’s SQLite holds a copy of session metadata (folder, titles, index time) and transcript content for search. It populates the cache on startup by scanning all JSONL files, and after that relies on `fs.watch` (as above) to detect new/changed files and call `refreshFolder`. Thus in normal operation it will stay up-to-date. If the process exits or misses an event, the worst case is that a changed transcript briefly wouldn’t be reflected until the next full scan. Crucially, Switchboard does *not* display any “aged” label on numbers. In practice we should assume the UI shows whatever its DB currently has – but the watcher means it should rarely be stale. (→ *OBSERVED*, [44], [46].)

- **Windows support.** Switchboard is cross-platform. It spawns PTYs via [node-pty](https://github.com/microsoft/node-pty), which works on Windows, macOS, and Linux. The code has special logic for WSL on Windows: when the shell is a WSL shell, it converts the project path to a `/mnt/` style path and passes it via `wsl.exe`. Terminals are Unicode/ANSI, and the app sets `TERM_PROGRAM=iTerm.app` to coax Claude CLI into sending its OSC notifications. We did not see anything in the code that outright disables Windows (on the contrary, it tries to detect `isWindows` and WSL explicitly in shell-profiles). In short, Switchboard *should* run on Windows; it was even explicitly designed to support WSL cases. However, its real-world behavior on Windows would need testing (the Node-pty+Electron stack is mature, so it should be fine). (→ *OBSERVED*, [40].)

- **Identity model.** Switchboard identifies sessions by the unique session ID (the JSONL filename) and displays names derived from the transcript. It shows a “session name” only if the user has explicitly renamed it via the UI; otherwise it uses any name found in the transcript (the customTitle or aiTitle from the `Title:` prompt) or falls back to a summary snippet. In the absence of a rename, multiple sessions with identical transcript titles would appear identical in the list (just with different IDs or folder context hidden). In practice, the displayed title is `(userName) + summary`; userName comes from a “rename” operation (`session_meta.name`). So our five “boot pre-flight verification” sessions would all show the same title unless renamed. In other words, Switchboard uses neither stable numeric IDs alone nor enforced unique names – it trusts the user (or CLAUDE_CODE_SESSION_NAME environment) to set the name. If that’s not done, duplicate names will confuse the operator (an observed issue for us). (→ *OBSERVED*, [6].)

- **Extension surface.** Switchboard has no plugin or scripting API. It’s a standalone Electron app whose behavior is coded in JavaScript. The only user-customizable things are configurations in its Settings and the sqlite data (e.g. star/rename). It does not define a plugin interface or publish IPC channels for others. Extending it would mean either modifying its source or sending CLI commands to it via some non-public API. In practice, to teach it about “lanes” or “claims”, we’d likely patch it or run it with a custom build. It does have some config (e.g. `getSetting('global')` etc.), but these are UI prefs (theme, shell profile, etc.), not domain concepts. (→ *INFERRED*, based on code structure – no plugin code found.)

- **Security posture.** The renderer process has **`nodeIntegration: false, contextIsolation: true`**, which is good practice. The app does not load remote web pages; it reads local files and runs local CLI processes. It uses [electron-updater](https://www.npmjs.com/package/electron-updater) in packaged mode, so it auto-downloads updates from a presumably secured GitHub Releases channel. The code strips dangerous `ELECTRON_` environment vars before spawning any child process. It opens Terminal links with a handler (not a new BrowserWindow). In short, its architecture is typical Electron desktop app – the attack surface is mainly local files and processes, which is by design (it *needs* to read transcripts). Assuming we trust the binary distribution and GitHub as updater, its security is probably adequate. Node-integration is off and context-isolation on (per [38†L133-L138]), so web content cannot execute Node. (→ *OBSERVED*, [38]; no obvious red flags beyond typical local-reader behavior.)

# 4. Core Substrate Issues

## 4.1 Identity & Liveness

We observed that **session identity** must be multi-part. Real systems often use a combination of _user-assigned names_ plus stable IDs. For example, tmux lets you `new -s name`, otherwise you get numeric IDs. VS Code’s Agent list shows “session name + workspace”. The general rule is: **allow user-friendly names for scanning, but ensure a unique ID under the hood**. In practice, we should (a) encourage assigning unique session names (or derive them from the task), (b) if duplicates exist, disambiguate by showing context (e.g. branch, or a numeric index), and (c) always display the underlying session ID in a tooltip or details view so we never lose track. As one Reddit user put it, he wanted “one overview of all running sessions with their status and which project they belong to” – implying that project/lane context is part of identity.

For **liveness**: a session can be *running-attached* (user has an open terminal), *running-orphaned* (agent still processing in background), *exited-resumable* (finished but transcript remains, can resume), or *exited-gone* (cleaned up). We must distinguish these: showing a session as “running” when its terminal is closed is misleading (per §1.5). Switchboard partially does this: it tracks `session.exited=true` on PTY exit and removes it from active sessions. But it doesn’t know about external sessions. A robust manager would check: if `sessions.json` says the agent is “idle” or “waiting” but no PTY is attached, mark it ORPHANED. If `sessions.json` says finished, mark it DONE. If there is no JSON record (moved), mark it GONE. 

In practice, we should **read both the session registry and the process table**. For example, `claude agents` output plus the JSON files could tell us “Clauses says: session X is kind=bg, status=waiting” (BG means no terminal). We can then label X as “background (input needed)”. Similarly, if no process exists for a listed session, we show “finished – can resume.” The UI should then allow “Resume” only for resumable sessions. If an attach is attempted on an orphaned session, the UI should warn “This session is running as background; please use Resume or --fork”.

## 4.2 Blocked-Question Channel

The core problem (§1.3) is *alarm absence*: agents are writing explicit questions in JSON, but humans never see them. UX research suggests this is very dangerous: **notifications requiring user action should be intrusive, not passive**. Switchboard’s use of OSC 9 maps to a “terminal-notification” event – presumably the UI could show a badge. According to Nielsen Norman Group, these are “action-required notifications” and should typically interrupt the user (modal or toast). In contrast, passive badges can be easily missed. In a multi-agent setup, we need a clear channel: options include a single “agent inbox” with messages queued, or per-session pop-ups, or even OS-level push notifications. 

One simple approach: whenever an agent asks for approval (permission prompt) or posts a question, the UI could flash the Dock/taskbar icon or a pop-up dialog saying “Session XYZ requests input: [question text]” with “Yes/No” buttons. That would satisfy the “action-required” criterion. Another approach is a merged queue (e.g. a list of all unanswered queries) so one person can triage them. Given we saw *four agents stuck with unanswered questions*, this must be fixed immediately. Implementing a UI badge is a start; ideally, short of a full modal, at least a system tray notification with the text and a click-to-open could ensure the operator notices. Research on multitasking suggests clearly labeling which session and showing context (current plan or task) is also helpful – e.g. “<project>: Asking about environment variable.”

When two agents ask simultaneously, we must queue them. Best practice is FIFO or priority (time since question) – but we must never auto-drop one. Possibly allow the user to “answer all” or “block all if they exceed some threshold”, but the hard rule is each sensitive permission needs a human decision.

## 4.3 Cost as a Signal

Now that we can measure **per-session cost** (§1.4), what do we do with it? The key insight (echoed in Keito.ai’s blog) is that raw cost alone is meaningless without outcome. We should combine cost with some productivity metric (lines changed, tasks completed, merge requests, etc.). Our example table shows very different token budgets vs commits between lanes. A useful supervision approach is “cost efficiency”: e.g. highlight if tokens-per-commit or tokens-per-word is out of line. Another is “budget vs spending”: set a provisional token budget per session/lane and alert before hitting it (Keito calls this “token budgets”). 

Concretely, the session manager could display “X tokens used, $Y spent” next to each session and compare to a baseline or to other sessions. If one lane is spending 5× more than average for similar output, flag it. We could also surface “tokens per AI-response” or “tokens per commit” metrics in the UI to let the operator question them. Spikes in usage could be annotated with the cause (long answer, looping). 

However, we must avoid “vanity” metrics: simply showing “high cost!” without context causes panic but no direction. Per Keito, the solution is to tag each agent *task* with its cost and evaluate ROI. For example, “Lane A used 1000 tokens to do 2 code reviews (500 tokens/review) vs. Lane B used 200 tokens for 1 review.” This helps decide if one lane is “worth it”. In practice, that means we should track cost at the level of user stories or commits if possible. If a lane does a merge, display “spent $C on this merge”. 

In summary: incorporate cost in the UI but paired with outcome. Set alerts or soft budgets (soft: warning, hard: stop agent if possible) per session. Distinguish expensive models vs outcomes – e.g. “this branch rewrite is $10 less than rewriting by hand” or vice versa. The UI could even show a simple “Cost per diff” gauge. 

## 4.4 Productivity Enhancements (Evidence-Tier)

Many ideas are floating around for how to speed up an operator managing multiple agents. Below we list candidate features, annotated by evidence quality or trap:

- **Pre-written prompt templates / specs** (Production/deployment wisdom). *Evidence:* Addy Osmani’s guide recommends starting each coding session with a clear high-level spec and letting the agent draft the rest. He also cites “Plan Mode” (a Claude Code feature) where the agent only plans, not executes, which enforces that planning-first workflow. This suggests operators should prepare prompt templates (a mini spec) to reuse when spawning new sessions. This is effectively building a “template” for session launch. This helps avoid wandering agents and saves time on repeated instructions. It’s a **best practice** (informed by real users and GitHub’s “spec-driven dev” initiative) rather than a formal study, but it’s widely recommended by developers.

- **Session branching (“forking”)**. *Evidence:* Switchboard itself supports `--fork-session`, and Claude has this built in. The idea is to snapshot a state and then diverge. This is similar to checkpoints in ML runs. While no academic study directly covers “forking an AI session”, user anecdotes (and the GitHub Spec Kit themes) imply it’s useful when you want to try two alternative prompts from the same context. **Pitfall:** it doubles token cost if both paths continue in parallel; should be used judiciously. 

- **Cross-session search.** Searching across transcripts is marketed by Switchboard (full-text search) – it indexes and lets you search messages. We haven’t evaluated this, but it’s unique. This seems obviously useful: if an answer was given in another session, you could find it. The evidence is “it sounds sensible” (and Switchboard *advertises* it). No independent research, so treat as *idea* with moderate plausibility.

- **Replay/Undo.** Few tools offer an “undo last agent action”. In structured authoring, REPL environments let you roll back changes. No known studies on this for chat AIs. It could be simulated by forking and replaying or by saving intermediate branch. It’s likely a nicety but low priority (and tricky to implement).

- **Checkpoints and branching (versioning).** Overlaps with forking: saving the entire chat history as a version/branch. Some UIs (like Immich agents concept, or Hypothetical “session timelines”) propose a version tree of agent interactions. Again, this concept is endorsed by GitHub’s spec work (docs as memory). The evidence is anecdotal but from top practitioners: e.g. save SPEC.md and re-feed it to the agent on resume. So we should allow “snapshot and restore”. It isn’t critical for the current small scale but is a known good practice.

- **Prepared prompt queue (backlog).** No direct citation, but some UIs (like VS Code’s “My Work” pane) allow the user to queue tasks. The GitHub Canvas idea suggests writing down tasks. We should consider letting the operator maintain a list of “to-do prompts” to feed sequentially (this could be as simple as a text file or an interactive to-do list in the UI). Workflows that reduce context-switching by planning ahead are generally beneficial (common sense).

- **Batch permission approval.** We explicitly cannot do this for secrets (per rules). For trivial file permissions, some “always allow” rule might exist (and indeed Claude CLI has `--dangerously-skip-permissions`). But batch approval crosses the red line for sensitive info. Evidence: None – best practice is to be conservative with credentials. We will *refuse* any design that batch-approves per-secret decisions.

- **Session handoff automation.** E.g. moving a session from one user to another, or exporting results as a PR. VS Code’s Agent docs mention handing off from local to Copilot CLI to Cloud agent. The idea is legitimate: for instance, after an agent finishes coding, convert its result into a PR (already done by Copilot Cloud). Handoff between people isn’t well studied, but processes like writing a handoff doc (even automated) are suggested in our inter-session messaging issue. This is more of a feature request than researched fact, but it aligns with Slack/Miro practices of passing work.

In summary, the **evidence hierarchy** is roughly:
- *Strong/Reported:* Session listing UI (VS Code/Agents), spec-first planning (Addy blog), GitHub “My Work/Canvas” posts, anthropic issue on siloing, NNGroup on notifications, AI cost-tracking blogs.
- *Weak/Marketed:* Switchboard’s own claims (do not count without source). Warp testimonials (marketing), Reddit opinions (anecdotal, as insight).
- *Inferred:* We draw general UI/CS knowledge (unique IDs, list-of-sessions views, budget alerts) without explicit sources, but based on standard design patterns and the above evidence.

# 5. What *Not* to Build

Given the constraints (Windows-first, small team, explicit approval for secrets, no silent stale data), here is what we would **refuse** to implement:

- **A platform requiring heavy ops or multi-user infra.** This is a small team; we cannot stand up a server or bespoke cloud service. An Electron (desktop) or even a simple Python+GUI solution is acceptable; Kubernetes dashboards or online SaaS are out.

- **Batch-approval of secrets.** Per rules, we *cannot* skip per-secret human approval. Any suggestion to override `--dangerously-skip-permissions` is off-limits. (We can, however, consider batch-approving harmless file reads or merging rule-whitelists in specific cases.)

- **A system that quietly shows stale status.** We must label stale data with age. We cannot build a UI that caches without context. So any switchboard (or other tool) view must clearly indicate “last updated”.

- **Ignoring current tools.** We already have some scripts (`factory/sessions.py`, `factory/runs.py` etc.) that capture claims and run outputs. We must not ignore those; the requirement said “only add to, not remove”. So our answer should not discard that instrumentation.

- **Assuming unlimited parallelism.** The spec says “three concurrent lanes” is our current max. So designing for 10 or 100 sessions is unnecessary. We should optimize for dozens at most.

- **Complex economy of scale metrics without grounding.** While we want to show costs, we should avoid presenting “tokens per hour” or “ML-powered latency” without pairing to outcomes. As Keito warns, cost metrics must lead to ROI, not just a dashboard of numbers.

- **Any approach that increases human cognitive load.** For example, requiring the operator to memorize numeric session IDs or manually track numerous threads in a separate system is counterproductive. The UI should reduce not increase context-switching.

# 6. First Action

**Adopt Switchboard and connect it to our system.** In practice, the first concrete step is to install Switchboard on our Windows development environment and point it at `~/.claude/projects`. Then **test its session list**: launch a couple of sessions (with known names or CLAUDE_CODE_SESSION_NAME set) and see how they appear. This will immediately highlight gaps (e.g. identical names, missing alerts). 

While integrating, ensure Switchboard’s **session list includes our lanes** correctly – it likely will, since it reads the same JSONL transcripts we produce. Next, tweak it to better support our model: for example, modify it (or a small wrapper) to parse our `sessions/*.json` registry so that orphaned sessions show as “running (background)”. Then implement in the UI some indication for an agent blocked on a question (likely via the existing OSC9 hook). We should also enable cost stats (click the `/stats` toolbar button) to make sure per-session cost displays.

Once Switchboard is partially working, we can **retire most of our home-grown UI plans**. We would keep our existing CLI scripts for data but use the Switchboard window for the operator. If needed, we can also run Switchboard in “setSWITCHBOARD_DATA_DIR” so that it doesn’t conflict with any official build and can be modified.
