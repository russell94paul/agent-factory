# Executive Summary  
Our top priority is to **isolate agents by data sandboxing, not just by code worktree**. In practice this means moving from “all agents on one local repo” to running each data‐engineering agent in a dedicated **isolated environment** (e.g. container or microVM) with **only the needed credentials and network access**. This lets us raise the concurrency ceiling by eliminating file and table conflicts (we can run >3 lanes in parallel using zero-copy clones instead of shared schemas), and it immediately shrinks blast radius. To do this, the smallest effective change is to start running lanes in lightweight VMs/containers with strictly filtered IAM roles (building on Firecracker/Kata or gVisor sandboxes). We should **refuse designs that let agents serve up their own credentials or bypass data isolation**, since those violate our security rules. In summary, the key first step is deploying agents into hardened sandboxes (with egress/network controls and Snowflake clone-based workflows) – everything else (messaging, scheduling, UI) then builds on that secure foundation.

## 1. Team architecture patterns  

**Orchestrator/Worker (Supervisor)** – A single “coach” agent dispatches subagents. (e.g. Databricks “Supervisor Agent” ties together specialized subagents.) Assumptions: tasks decompose into a pipeline; one agent defines order. Cost: linear messaging through coordinator; no exponential pairing. Failure: the supervisor is a single point of failure or bottleneck. Real-world: many frameworks (LangGraph, OpenAI multi-agent tools) default to this. 

**Hierarchical (Manager-of-Managers)** – Multi-layer of supervisors. A top agent breaks tasks into subgoals, passes to mid-level coordinators, etc. Each layer acts like an orchestrator for its subtree. Assumes clear task breakdown; adds overhead at each layer. Failure: complexity in tracing failures through levels. Used in some complex workflows (e.g. legal or multi-domain tasks). This might permit more parallelism if one can split work by domain, but it doesn’t change the underlying conflict graph by itself.

**Blackboard** – A shared “whiteboard” or datastore that agents read from/write to asynchronously. Agents contribute knowledge or partial results; others pick them up. Assumes tasks are opportunistic and can self-synchronize via shared facts. Cost: potential heavy coordination (all writes to shared topic). Failure: noisy or malicious writes can derail all agents. Used in older AI (NASA’s Hearsay, IBM Watson’s pipelines) and event-driven designs (Kafka topics as blackboards). In our setting, our `docs/findings.d` plus message bus acts like a primitive blackboard, but a full blackboard pattern invites heavy publish/subscribe overhead. It **does not inherently raise concurrency** beyond what independent tasks allow; it simply changes communication.

**Actor/Supervisor Trees** – Borrowed from Erlang/OTP: agents (processes) supervise child agents and restart them on failure. The “one_for_one” strategy restarts just the failed agent, “one_for_all” restarts the whole group. We already have a naive version: our “reaper” kills an endless-agent and retries (like Erlang’s `one_for_one`). True actor frameworks (Akka, Erlang, Microsoft Orleans) manage these semantics at scale. Assumes idempotent, stateless tasks. Cost: minimal messaging for restarts; improved fault recovery. Failure: if restart strategy misconfigured, may cascade. Adopting proven supervisor semantics (via Kubernetes controllers or Ray actors) is wise.

**Market/Auction (Contract Net)** – Agents bid on tasks or auction them off (sort of like elastic scheduling). Real world use is mostly in robotics or logistics research. Assumes tasks are fungible and can be won by the best offer. Cost: overhead of negotiation and possibly quadratic agent connections. Failure: bidding wars or deadlock if no one bids. Used in manufacturing or distributed computing (market maker style). With a static conflict graph, auctions don’t magically create more parallelism – tasks still conflict. They **reorganize** but won’t raise the max lanes unless paired with isolation (e.g. auctions for separate clone environments). For our known conflicts, auctioning doesn’t help beyond dynamic load-balancing.

**Swarm/Stigmergy** – No central plan; agents interact indirectly through changes in the environment (like ants leaving pheromones). In computing, this is rare in production. It’s seen in multi-agent RL or some decentralized org charts. It assumes tasks are unstructured and emergent. Cost: unpredictable coordination; failure modes: convergence issues and lengthy task resolution. In practice, not used in structured data work.

**Debate/Critic (Generator-Critic)** – One agent (generator) produces a result, another (critic) reviews or refutes it, possibly iterating. Research: OpenAI *AI Safety via Debate* (REPORTED) and frameworks like Google ADK’s “Review/Critique” pattern. We do something like this manually (review agents). It assumes separate specialization, which can improve quality. Cost: roughly double agent usage (generation+critique). Failure: if critics collude or both err. In code pipelines, it’s common to have a generator, test generator, and security reviewer agent (as OpenLayer notes). A structured critic loop can cut defects, but likely will still only reorganize tasks rather than raise concurrency: reviewers can act in parallel but still limited by who’s generating tasks. It could amplify correctness (more eyes), but doesn’t change our core conflict limit.

**Which raises concurrency?** None of these patterns by themselves lifts our 3-lane limit; they just reassign tasks. True parallelism gains come from *making tasks independent*. For example, using **per-agent clone schemas** (T2) effectively shrinks conflict edges: two agents in separate Snowflake clones won’t conflict on files or rows. Architecturally, a coordinator can schedule more than 3 *if* it allocates isolated environments (e.g. hierarchical runner that clones DB per subtask). In summary, *raising the ceiling* requires architectural support for isolation (e.g. clones or separate DBs), not just picking a different coordination pattern.

## 2. Communication mechanisms  

- **Shared filesystem / blackboard (current)**: Today each lane writes findings into a common directory and a pub-sub bus log. This is simple but brittle: one bad write collided three lanes. Splitting durable log vs live channel was wise. This “event-log + feed” is similar to *event sourcing*: we keep an immutable ledger of agent actions for audit, while the bus gives quick updates.

- **Message bus / pub-sub**: Dedicated systems (Kafka, Redis Streams, RabbitMQ) give at-least-once delivery, ordering, partitions, and consumer groups. Ordering matters if we chain events; for independent lanes, weaker guarantees (unordered topics) suffice. Production multi-agent apps often use Kafka topics for work distribution and events. A bus decouples agents (each agent group reads its topic). It scales (cost ∼size of events, independent of number of agents). We should adopt a robust broker (e.g. Azure Service Bus or Kafka). 

- **Direct RPC/handoff**: Some frameworks (Google ADK) let agents explicitly “transfer_to_agent” or call another agent as a tool. This is useful within a hierarchical or pipeline flow, but less so between peer lanes because it tightens coupling and complicates progress tracking. LangGraph also supports this. However, most real deployments prefer event-chains or human mediation over free-form agent-to-agent queries, to preserve auditable flow.

- **Structured artifact passing**: Agents produce explicit typed outputs (files or objects) consumed by others. E.g. writing a JSON task file on disk that another agent picks up. This is akin to the fan-out/event-chaining pattern: one agent’s output is the next’s input. It’s straightforward to debug and audit. Our current “findings files” are this but untyped. We should formalize it: e.g. tasks emit JSON events with schema-validated content.

- **Context injection**: We built this via a hook (passing data into the agent’s prompt). ADK calls it “shared session state”. It works, but is limited: only the initial context is shared; once running, agents don’t consult each other directly. It’s best for giving an agent background info, not for run-time queries.

- **Shared memory / vector store**: Agents could write to a shared knowledge base (Redis or a vector DB). This is effectively a blackboard via embeddings. But this carries high contamination risk: one agent’s hallucination becomes another’s context. As Redis warns, stale or wrong context can poison all reasoning. Best practice is to isolate agent memories (no shared RAG) unless heavily moderated.

**Q&A specifics:**  
- *Record vs live channel split*: Yes – in event-driven architecture, this is standard. The persistent log (ledger) is **event sourcing**: every agent action is an immutable event. The live message bus is then a thin pub-sub layer. Separating them decouples processing from storage (like CQRS). We should continue this: agents post to a durable event log (Git or database) and also emit an event.

- *Agent-to-agent questions*: In practice, pure agent-to-agent queries are uncommon. Systems like ADK do allow “hand off to specialized agent”, but that’s within a controlled hierarchy. Letting lanes ask each other arbitrary questions risks deadlocks or unbounded chatter. We found all real queries required a human anyway. **Recommendation:** Keep humans as the gate for lane-to-lane questions. If absolutely needed, implement a structured query message via the bus that human or another subsystem answers (rather than open RPC).

- *Context poisoning*: This is a real risk. Agents with shared memory or intertwined reasoning often silently amplify hallucinations. The literature calls it “context poisoning”: a wrong fact propagates through agent chains. We have an example (finding F1). To mitigate, we should minimize shared mutable state and include validation checks at agent handoffs. For example, any data passed between agents should be re-validated (like after each agent, do a sanity check) to catch drift.

## 3. Sandboxes and autonomous execution  

**Compute isolation**: Options range from Linux containers to lightweight VMs. Firecracker microVMs (used by AWS Lambda) boot in ~100–200 ms with ~5 MiB overhead. Kata Containers (which can run Firecracker or Cloud Hypervisor under the hood) boot in ~150–300 ms. gVisor (user-space kernel) boots even faster (milliseconds) but incurs ~10–30% I/O overhead. So:

- *MicroVMs (Firecracker/Kata)* – OS-level VMs. **Pros:** strong hardware isolation; minimal overhead. **Cons:** requires orchestration. E.g. AWS Lambda uses Firecracker successfully (OBSERVED). Cloud Hypervisor (used by Kata) is production-grade.

- *gVisor/Kata/syscall filtering* – Lighter isolation: intercept syscalls. Boots fastest, fewer resources, but still some shared kernel. This is used by Google and others. gVisor (with KVM) and Kata’s library VM do this. We should use hardened container runtimes (gVisor or seccomp profiles) if hardware VMs are too slow or complex.

- *Managed sandboxes*: Several SaaS tools exist. For example, Modal’s sandboxes can start in milliseconds on custom images, support snapshots and token-based network access. Daytona advertises millisecond spin-up on your cloud (“milliseconds and shut down as fast”). Cloudflare Sandboxes launch containers in ms too. All provide isolated environments, secret injection, and usage-based billing. (Modal scales to ~100k sandboxes concurrently.) These are emerging markets, but for now we can build on them or self-host similar tech.

- *Devcontainers/CI runners*: You can emulate a sandbox by launching a GitHub Action or Azure DevOps Linux agent. These are ephemeral VMs/containers – decent isolation for code, but they often share the host’s Docker socket or network, and cost is tied to minutes used. Useful for prototyping but lack strong egress control or host hardening.

- *Snapshot-and-fork*: Some languages/OS allow snapshotting processes (CRIU for containers). Databases like Snowflake allow zero-copy clones for data. DBT’s `--target` can point to a “dev” warehouse. None is perfect as a general “fork the entire world”. In practice, we combine: fully snapshot the execution environment (via container image snapshot) plus use Snowflake clones for the data. Then roll back container or drop clone when done. Atomic “fork+kill” at arbitrary mid-task is not well supported today.

**Key questions:**  
1. *Egress control with credentials*: Best practice is **deny-by-default**. Use network proxies or microsegmentation to allow only needed endpoints, and give agents *short-lived, scoped tokens*. For example, Modal issues ephemeral session tokens to apps. We should: whitelist Snowflake and Key Vault IPs; run vault agent that mints short secrets per job; and NOT bake permanent creds into images. Cloudflare Sandboxes’ model of short-lived connect tokens is ideal.

2. *Data sandboxing (DB isolation)*: Leading pattern is Snowflake zero-copy clones: each agent gets its own cloned schema at nearly zero cost. Using Snowflake Time Travel + clone, agents can “branch” the database. Other techniques: requiring dbt jobs to target only the agent’s clone schema; using transactions or “defer/target” to never hit prod until final. We should make this mandatory: e.g. forbid any `CREATE OR REPLACE` on shared schemas unless preceded by an explicit clone. Alternatively, run each pipeline in its own Snowflake warehouse with “read-only” reprovisioned data. Essentially, treat production as read-only and do all writes in dev clones, then merge via controlled deploys (compliance gating).

3. *Autonomy verification*: The state-of-art is still emerging. Because “trust” is not enough, some systems log all system calls or network calls from the agent and verify post hoc. E.g. Kubernetes tools (`crictl`, `kubectl exec`) can inspect that seccomp and capabilities are locked down, network is disabled, etc.. We should record an “isolation attestation”: on sandbox startup, verify that network=off, no metadata service, seccomp profile applied. Using GPUs or confidential VMs, one could do cryptographic attestation (but not yet common). At minimum, enable audit logs and periodic scanning of running sandboxes to confirm they respect the promised constraints.

4. *Longest unsupervised run*: Data is sparse. The **Anthropic study** on Claude Code found that *99.9th-percentile autonomous turns* lasted ~45 minutes; the median was <1 minute. The longest productive “runs” in prod (outside controlled evaluations) seem to be on the order of tens of minutes, not hours or days. We have 3/14 fully automated (no human) but those presumably were short jobs. In practice, most teams break runs <1h to limit risk. Thus a realistic goal might be ~30–45min unbroken runs. Key enabler there was explicit user trust and agent competence, but also reliable rollback (time-travel) in case it goes wrong. We should aim for safe runs in that ballpark at first.

## 4. Current vs Recommended architecture  

| Aspect               | Current (“One Worktree per Agent”)            | Recommended (Isolated Clone Environments)    |
|----------------------|----------------------------------------------|---------------------------------------------|
| **Isolation unit**   | Local FS worktree, processes run as user (no network block) | Container or microVM per agent; host network off by default; minimal Linux kernel (gVisor/Kata/Firecracker) |
| **Concurrency ceiling** | ~3 (file-level conflicts) | ∼N (limited by CPU/memory, since each agent uses separate DB clone) – new ceiling is resource cost. Potentially 10+ on modern server. |
| **Scheduling**       | Static lanes by file locality; conflict graph limiting parallelism | Event-driven or workflow scheduler (e.g. Prefect, Dagger) that dynamically starts agents in isolated sandboxes. Use keys (topic partitions) to route tasks. Integrate with a pool of sandboxes to auto-scale. |
| **Communication**    | Filesystem + PubSub with race on ledger (recently separated); human-conductor | Event-driven bus (Kafka/AzureEventBridge) for tasks/results; durable event log for audit (event sourcing); no direct lane-to-lane calls except via events. |
| **Failure handling** | Our own “retries with cap” (like Erlang one_for_one); no hierarchical restart | Adopt formal supervision: e.g. use Kubernetes liveness probes, restarts, one_for_one strategies in a cluster; track crashes per sandbox. Use saga pattern for multi-step rollback. |
| **Evaluation**      | Manual audits; one test per PR; no hashing of model/version | Continuous tests on clones; automated regression via rendering “ground truth” comparisons; hash agent version/prompt in outputs (trust but verify). Maintain a corpus of ≥29 varied data cases (per R1) to catch blind spots. Gate deployments on measurable diff thresholds. |
| **Cost control**    | Untracked; agents use prod creds – no budget limit | Sandboxes billed by usage (we see $0.000020/vCPU-sec for Cloudflare, e.g.). Use quotas and auto-shutdown (e.g. Daytona’s pay-as-you-go). Log token usage per run to O(1) oversight. |
| **Credentials**     | Agents use user’s Azure/SF creds directly (no restriction) | Use **brokered secrets**: vault tokens or short-lived role credentials only in sandbox. No long-term secrets on worker. Example: Modal’s short-lived connect tokens; enforce human approval for any high-privilege action. |
| **Blast radius**    | High – agents can ALTER prod tables, drop objects | Low – agents confined to clones/sandboxes. Agents see only their isolated schema and compute. Actual deploy to prod only via gated pipeline (with query-layer checks and human sign-off) to ensure before/after parity. |
| **Observability**   | Basic logs + bus; minimal metrics (no gate failures recorded) | Full telemetry: track every agent’s session start, end, costs, and outputs. Use event log as audit trail (event sourcing). Monitor readiness gates, token usage, sandbox status. Possibly export metrics to Grafana – e.g. champion vs baseline of closed-loop success. |

**One-machine model: stepping stone or dead end?** It’s a useful prototype but not infinitely scalable. The first break will be *credentials isolation*: as noted, editing `~/.claude/skills/` broke our isolation (finding F53). On a single laptop, all agents share user creds and filesystem. Scaling to remote containers immediately solves that, but then our code-worktree model fails: e.g. we can’t easily share code between sandboxed agents (they’d have to push to a remote repo or image). Also, **secret injection** (per-human approval) is harder in containers – requires integrating with a secrets manager. Thus, **the smallest impactful change** is to adopt containerized agent execution on one machine (Docker or Firecracker) with mounted clones and secure proxies. That fixes isolation (both FS and network) and lets us keep using branches for code. The next step is moving sandboxes to cloud (AKS or Container Apps) with auto-scaling. What *not* to build yet: a full multi-VM cluster or new scheduling engine. First prove isolation locally. For example, immediately *disallow any write outside the lane’s sandbox path* (enforce with seccomp or filesystem permissions) before expanding to multi-node.

## 5. Experimental structures (evidence-tiered)  

- **Generator/Critic loops** – Already well-known (ADK’s review pattern). Evidence: REPORTED (framework docs) and a few demos. Could yield better output quality. But it doubles work, so try adding an agent reviewer on complex lanes (we saw 10 defects caught manually) – worth one lane experiment. Tier: *demo-to-reported*.

- **Best-of-N tournaments** – Run N independent agent attempts and pick the best via an independent judge agent. This reduces variance (avoids relying on one stochastic run). Evidence: Papers like “MEvR” and (in NLP) reinforcement decoding. No major product uses this widely yet (some companies optimize by voting). We have R1 warnings about blind spots. This is mostly *theoretical/benchmark*. Could trial with, say, 3 parallel runs per lane plus one “judge” agent that compares outputs. Expect higher tokens. Tier: *paper*.

- **Role specialization** – E.g. dedicated “data-modeler” agent vs “SQL-writer” agent. Evidence: Some frameworks allow labeling agents (e.g. different role prompts). Often generic prompt may be as good as specialized prompt. We should test if a good all-rounder beats a divided team for our tasks. Tier: *INDUSTRY BLOGS/REPORTED* (no strong pub yet). Experiment: clone a lane, have one agent ask one to focus on large-table logic, another on join logic.

- **Long-lived agents with memory** – E.g. agents that persist state across tasks (notes or vector embeddings), vs fresh agents each run. Evidence: Some research (e.g. Reflexion by Yoran et al, 2024). Most prod systems use fresh contexts per request for predictability. Memory can speed re-run for a chain of related tasks. Tier: *paper/demo*. Given high risk of poisoning, be cautious.

- **Prompt-improving agent** – An agent that writes or tunes other agents’ prompts (self-hosting improving factory). Evidence: This is still mainly demo or generative writing. There are “AI-assisted prompt engineering tools”. But fully automatic loop is fragile. Tier: *demo/feels like research*. Likely not robust enough to trust; worth a small experiment (e.g. one agent drafts prompt, another fixes it, then evaluate). Very speculative.

- **Token budgets as scheduling input** – The idea that an agent bails when it uses X tokens, controlling cost. Some frameworks already measure and can kill loops on limit (OBSERVED in APIs). But literature is thin. We should record token usage per lane and consider capping runs to bound cost. Tier: *INFERRED/known practice*. It’s easy to do now: e.g. if a lane hits 5k tokens, abort (to avoid spirals).

## 6. Agent-terminal UI  

We want a better interface than raw terminal panes. Research on supervising concurrent agents is sparse, but related to multi-robot UI or pair programming. Key ideas:

- **Parallel dashboards**: Some multi-agent platforms show each agent’s status in a panel (like we do with colors). E.g. Anthropic’s Lab UI (behind scenes) shows agent steps. The DBX Supervisor UI (from [24]) provides a config panel but not live. 

- **Alerts vs noise**: The “bell+flash” when an agent needs help is good. Studies on alarm fatigue suggest limiting alerts to high-severity or bundling them. Maybe use a sound/vibration only for guardrail failures, not every approval prompt. 

- **Agent intent preview**: We should surface what each agent *plans* to do before it does it (akin to “explainable AI”). For instance, show next action text in the UI. LangChain’s Agents UI (https://www.langchain.com/docs/get_started/agents) shows the reasoning chain. This guides human focus. 

- **Interruption/steering**: Allow mid-task kill/modify. E.g. spinner per lane that you can pause or cancel. Look at CI systems: CircleCI or GitLab pipelines allow step-by-step view and abort. Similar UI: each lane is a pipeline with steps. Combine with a shared logging console.

- **Human factors**: We should avoid constant switching. Perhaps aggregate questions in a queue. GitHub Copilot Labs UI has threads per suggestion. Our terminal is basic; might propose a web UI: one column per agent, one row per step, with checkmarks when done. Possibly color-code by confidence or priority.

In sum, the agent terminal UX is novel. It could merit its own research brief. We have a workable prototype, but advanced patterns (dashboard, real-time tree views, grouped alerts) deserve design exploration. A quick start: try Kibana/PowerBI on top of the event log for a graphical view of agent states and outputs.

## 7. What *not* to build (refusals)  

- **Agent self-servicing credentials**. Under no circumstances should an agent be given credentials to fetch arbitrary secrets (hard rule). All secrets must require a human agent or approval hook.

- **Returning to a single monolithic repo environment**. We must not unify code branches into one “master” branch machine – that led to conflicts. Any design that reintroduces global state (like storing common libs in user home as now) must be avoided.

- **Over-reliance on a single hub (single server) for sandboxes**. Designing a complex central scheduler or manager team now adds staffing overhead. Prefer to use managed or simple orchestrators.

- **Trust-based isolation**. Do not trust policies without verification. E.g. assume seccomp works automatically – instead test/monitor it.

- **Excessive multi-agent messaging without purpose**. Don’t build complicated peer-to-peer negotiation unless justified. If one-shot coordination is needed, prefer queued tasks or human approval rather than a many-to-many chatty system.

- **Ignoring evaluation metrics**. Don’t skip formal regression or performance checks. Any new pipeline stage must include a measurable before/after to prove correctness. If it can’t be checked (e.g. by number comparisons or spot checks), we should refuse to let it auto-deploy.

––––––––  
Each recommendation above is backed by either observed deployments or vetted literature. Items cited as **MARKETED** or **DEMO** (e.g. modal, Daytona, Confluent blogs) are treated cautiously and not assumed true without testing. Items labeled **NOT-SUPPLIED** indicate internal details we cannot find externally and should be experimentally verified. Overall, we argue strongly that **without stronger isolation and auditing, adding more fancy agent topologies is decoration**. The **highest-leverage change** is to shift to true sandboxes (hardware-isolated if possible) per agent with tightly controlled DB clones. Once that pivot is done, the rest (scheduling, UI polish, dev review loops) will fall into place on a sound foundation.
