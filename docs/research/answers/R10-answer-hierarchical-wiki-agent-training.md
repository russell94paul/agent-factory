# Verdict  
Given our ~1.1M-token wiki, the **generic-agent + wiki** idea sounds plausible in theory but fails in practice.  Key constraints kill it: large-context limits and hallucination risk.  State-of-the-art LLMs degrade sharply with very long contexts, so feeding our entire wiki is unworkable (performance fell ~24% with just 30k irrelevant tokens).  Retrieval (RAG) *can* inject knowledge, but it shifts complexity to indexing and quality-gating.  Crucially, *unsupervised* wiki expansion almost certainly corrupts the knowledge base: even small errors get “laundered” into memory and silently mislead downstream agents.  In short, without a robust fact-check gate, auto-writing compounds mistakes; with one, the system gains little.  At our scale (and team size ~4), the tower of extra infrastructure (a new knowledge graph or vector store) is unjustified.  Instead, we should consolidate and improve what we have (better retrieval, skill synthesis) and fix the control plane first.  

The single most damning fact is the *memory-laundering* phenomenon: an LLM can summarize or rephrase hallucinated content into “innocuous” language that still misguides later reasoning.  With our wiki as *state*, a similar effect will corrupt it silently unless every write is rigorously verified.  No lightweight auto-loop can safely guarantee that.  Thus **“eventually” it *will* corrupt the knowledge** unless we invest heavily in gating.  Given our current readiness (few passing gates, no cost instrumentation), we can *observe* early signs: e.g. a rise in contradictions or reliance on auto-generated text.  

**Bottom line:** *Don’t build a fancy hierarchical auto-updating wiki before we fix the basics*. The evidence suggests *RAG and structured context can help, but only if carefully controlled*.  The expensive investment in a new store or auto-researcher should be deferred until we have sandboxing, evaluation metrics, and gating in place.  In other words, **this does not “work” yet at our scale**; the real leverage may come from distilling our wiki into executable skills (Mechanism E) or just patching prompts, not a second wiki.

## 3. Hierarchy: Load-bearing or Decoration?  

The evidence suggests structure *can* help, but with diminishing returns at our corpus size (∼1M tokens).  When knowledge is very large or queries are complex, hierarchical RAG (graph-based indices, multi-hop retrieval) clearly outperforms flat retrieval.  HippoRAG (NeurIPS’24) reports ~15–20% better multi-hop QA accuracy than baseline RAG by using a multi-resolution KG and PageRank.  Context Engineering also found that *explicitly structuring context* nearly doubled first-pass success.  That implies our entity/concept/process graph could improve reasoning efficiency by guiding the agent to the right “altitude.”  

However, these gains incur costs.  Indexing overhead grows with corpus size and change frequency; GraphRAG-style static graphs falter on frequently-changing data.  Maintenance is heavier if we keep a knowledge graph of projects/tickets.  More critically, context-limit research shows a counterintuitive effect: beyond a few 10s of thousands of tokens, *even perfect* context retrieval can *hurt* LLM reasoning.  In one study, Llama-3’s accuracy dropped ∼24% simply by adding 30k irrelevant tokens (even though relevant info was present).  This “too much context” problem emerges well below our wiki’s size, so **naïvely injecting 100k–1M tokens into prompts is detrimental**.  

**So where’s the sweet spot?**  For our corpus, it’s likely **in between**.  We cannot paste the whole wiki, but we also can’t index every tiny page in a KG.  We should group related content (e.g. cluster entity pages by project or stage) and retrieve in chunks no larger than ~20k tokens total.  If we do employ a KG, it should encode *key concepts and process steps*, not every markdown file.  As an analogy, enterprise data catalogs (Amundsen, DataHub) *do* build knowledge graphs of datasets, pipelines, and schema relations, but they still limit graphs to top-level assets and lineage.  We can borrow that approach: treat our wiki’s hierarchy (entities → processes → tickets) as a multi-hop retrieval path.  

**Hierarchy vs flat at 1M tokens:** Given that 1M is *order-of-magnitude larger* than known safe thresholds (~25k), some retrieval is mandatory.  Graph-based RAG (like HippoRAG or GraphRAG) likely exceeds our needs; even HiRAG’s three-level retrieval might be overkill.  Instead, we recommend a **mini-hierarchy**: use the wiki’s existing outline structure (entities/concepts as parent nodes, with links to specific procedures or tickets) to assemble context.  For example, if an agent is working on “Salesforce data flow,” first retrieve the “Salesforce integration” concept page plus any linked daily notes, then descend into the specific tables/process docs.  This structured routing (Mechanism C) is costlier to implement than flat vector search, but it aligns with our domain’s logic.  The evidence (context engineering, GraphRAG) says *any consistent structure* beats none; we should choose the cut that maps to user mental models (entity→process→ticket) and reuse existing front-matter tags for filtering.  

In summary: **Hierarchy can be load-bearing for complex tasks, but at our small scale it’s primarily a retrieval *quality* booster, not a necessity for capacity.**  We should lean on it to improve prompt focus, but not invest in building a full ontological KG or refactoring all content.  Existing practice (tags, link graph depth) provides a usable structure; what matters is *using* it in retrieval.  Graph-aware RAG methods (GraphRAG/HippoRAG) are promising templates, but we must weigh them against implementation cost and data staleness.  

## 4. Auto-Researcher Loop: Compound or Corrupt?  

Unchecked, an auto-researcher **will corrupt the wiki**, not improve it indefinitely.  This conclusion comes from multiple strands of evidence:

- **State Leakage and “Memory Laundering” (OBSERVED):**  Agents compress and transfer knowledge between sessions.  Recent work shows that *unsafe or false info can hide in that memory:* Shwartz-Ziv et al. find that summarizing toxic content into “harmless” text still led downstream agents to behave toxically.  By analogy, an auto-agent could write a plausible but incorrect fact (flavored as a neutral statement) into the wiki; the next agent, trusting its context, would build on it as if it were true.  This “laundering” is insidious: standard filters wouldn’t catch it once it’s paraphrased.  Only aggressive sanitization *before* adding to memory prevents it.  We have no equivalent sanitization in our plan, so any hallucinated fact will likely seep through.  

- **Hallucination Propagation (REPORTED):**  Even with RAG, LLMs hallucinate.  The RAGTruth corpus (Niu et al. 2024) quantifies how “word-level hallucinations” persist in generated answers.  They show a fine-tuned model can *detect* hallucination, but only after careful training on annotated data.  Importantly, the existence of RAGTruth implies that **vanilla RAG does not guarantee factual output**.  In our loop, an agent might confidently add wrong statements (especially if they “made sense”) unless we build a critic.  Without an explicit hallucination detector, we risk snowballing errors.  

- **Compound vs. Decay (ASSUMED):**  No public study shows a self-improving corpus “gets better forever.”  In fact, analogous domains suggest the opposite.  Machine-generated data tends to be low-entropy; feeding it back can collapse a model’s diversity.  E.g. in “auto-generated knowledge” settings (like continually updated wikis), teams have observed *drift* and echo-chamber effects, though systematic benchmarks are scarce.  Meanwhile, systems designed for iterative improvement (DeepMind’s Reflexion, AutoGen, or Voyager) do refine their outputs, but always rely on strong grounding (environments, human feedback, or reward signals), not blind wiki writing.  We did find that auto-synthesized artifacts **can** improve single-round performance: Mem0’s graph-memory showed consistent gains on QA, and SkillX’s iterative refinement improved their agent’s Pass@4 by several percentage points.  However, those are *direct learning gains*, not endless loops without human input.  There's no evidence that an unsupervised loop like our wiki *improves* itself; instead, we see a high risk of compounding hallucination.  

- **Provenance and Tiering (PUBLISH):**  Our own best practice is to label each page’s evidence (Measured, Derived, etc).  No prominent agentic system we know of enforces page-level provenance that guides retrieval.  (Graphiti does track “when an event occurred vs ingested time”, but that’s metadata for consistency, not trust per se.)  In short, retrieval layers rarely use intra-corpus provenance.  So *even if* we mark wiki pages by reliability, the agent might ignore that.  Practically, we should treat the wiki as scratch space, not gospel.   

- **Write Gate (DESIGN):**  If we did try an auto-writer, we need a “gate.”  Human review of each new page is infeasible.  The literature offers few ready-made solutions.  Options include: (a) a separate AI “critic” to fact-check each entry (e.g. using RAGTruth-trained verifier), (b) a quarantine zone (flag auto pages for limited use), or (c) only allow high-precision sources (e.g. vendor docs) to be used directly.  The cheapest, evidence-backed idea is a *small model fine-tuned on hallucination detection*.  For example, Niu et al. showed a finetuned LLM could suppress hallucination comparably to GPT-4-level prompt checks.  We could apply that as an automated filter: any generated wiki content scoring low confidence gets discarded.  It’s not foolproof, but it’s concrete.  

- **Contamination Modeling (DERIVED):**  Suppose our auto-agent writes 100 new wiki pages per month, and even 10% of each page is fabricated.  That’s ~10 pages of errors leaking in.  Over a year, 100 error-pages would accumulate.  Because agents later use those pages as “ground truth,” every answer derived from them would be suspect.  We’d likely see an uptick in fact-check interventions and a drop in gate confidence without realizing the root cause.  This is analogous to **“dataset poisoning”** in ML: a small percentage of bad training data often corrupts the model’s outputs.  While we don’t have a numeric model, the qualitative point stands: *unbridled auto-generation will eventually drown truth in falsehood*.  

- **Correction Path (OBSERVED):**  When the wiki *is* wrong, Wikipedia’s social review is its cure.  In an automated pipeline, no such correction exists.  Graphiti shows one idea: flag edges as invalid with bi-temporal stamps.  In practice, we’d need something like that (e.g. date-tag each fact and expire old ones).  But even Graphiti’s AI-driven conflict resolution is still experimental.  We should assume: if an auto-page is wrong, it *stays wrong* until someone notices.  

**Conclusion:** Without a strong write gate, the loop **corrupts**.  We must either not write back at all, or gate every write with something like formal verification or human oversight.  If we choose to proceed, even semi-automatically, we should adopt a “prefer miss, not hallucinate” strategy: let agents skip writing questionable content.  In practice, this means **disabling auto-research writes until gating exists**.  

## 5. Write-back of Work-derived Knowledge  

Agents in our pipeline often discover unique facts during execution (e.g. “ticket premise was wrong,” or “dashboard reads Table X not Y”).  Capturing this is crucial, but raises similar issues to auto-research.  Evidence on “live discovery vs curated research” is scarce.  Intuitively, **measured facts are more reliable than synthesized ones**, but we found no study directly comparing them.  We assume work-derived knowledge is higher quality per token.  For triggers: best practice (cf. Mem0, Graphiti) is to write **only when the agent detects a conflict or new insight**.  For example, if an agent finds the dashboard source differs from wiki, that should trigger a wiki update.  Conversely, redundant or obvious findings should not bloat the wiki.  

Representing corrections is tricky.  We can borrow the bi-temporal idea: each wiki entry could carry a “valid from” date and “valid until” (if superseded).  The retrieval system would then ignore entries whose validity window has closed.  Alternatively, we could maintain a “deprecation” flag in frontmatter and have the context assembler skip those pages.  Unfortunately, typical LLM retrieval ignores such metadata, so a more robust solution would be to treat the wiki as a database with versioning: e.g. replacing old claims rather than appending contradictory ones.  Another pattern is “claim-level versioning”: break each wiki page into atomic statements with their own status tags.  That’s complex; the simplest path is to require any agent write to *link to the specific source/ticket* and to *mark supersessions in frontmatter*.  We should at least design the schema now so future indexing can honor “validity intervals” (as Graphiti does).  

In summary: **write-back of discovered facts is valuable, but must be conservative.**  Only novel, verified findings should become wiki content.  Agents should ideally label any added fact with a timestamp and source, enabling future pruning.  We recommend *no automatic wiki writes during normal work until we have a gating mechanism in place*.  Instead, use a separate “finding” database (our ticket-evidence store) for new info, then have an (optional) editorial step to merge into the wiki.  

## 6. Measurement Plan (How to Know if It Works)  

We must treat this architecture as experimental.  A rigorous A/B test is needed.  **Design:**  Split a representative set of tickets or projects into two groups.  All agents and code tools are identical, but for the “Wiki‑on” group agents can access the hierarchical wiki (via retrieval, memory, etc.), while “Wiki‑off” agents do not (fall back on boot prompts only).  Each group should have ≥30 cases to catch ~10% effect sizes.  The **unit of observation** is one pipeline run (from ticket to deploy).  

**Metrics:**  Pure “task success” (does dashboard reflect correct data) is too coarse.  Instead, track intermediate proxies:

- *Human interventions:* Number of manual corrections per run (queried as “how many times did an engineer have to fix or clarify?”).  (No published analog, but it’s a natural measure of agent autonomy.)
- *Rewrite overhead:* Count of times the agent “rediscovered” a fact already in the wiki (redundant work).  Less rediscovery in Wiki-on is positive.  (This is akin to coverage metrics in retrieval systems.)
- *Hallucination count:* Number of wiki-based assertions the agent got wrong (detected by a human or automated QA).  We can adapt RAGTruth’s annotator tool to flag fact errors.
- *Conflicts flagged:* How often did downstream tests fail (e.g. data tests, budget checks), indicating agent drift.  Compare fail rates Wiki-on vs Wiki-off.

Some of these (like “redicovery”) are novel metrics for us.  The only precedent is memory benchmarks where they measure “reuse of memory” vs “new computation”.  We’ll have to define them and instrument our logs carefully.  

**Leading indicators of corruption:**  We should monitor the wiki itself.  Possible signals: (a) *Growth ratio of auto-generated content*: fraction of pages flagged as auto-written over total.  (b) *Contradiction density*: run a consistency checker (e.g. claim extraction + contradiction detection) periodically to see if new pages conflict with old.  (c) *Citation concentration*: if many pages cite only a few automated pages, that suggests echo-chamber growth.  A rapid rise in any of these could flag trouble.  There’s no standard measure published, so we must define thresholds ourselves (e.g. “>10% contradiction rate” or “auto-pages >20% of references”).  

**Falsification criteria:**  We must specify what outcome in 30 days would falsify the concept.  For example: if after two iterations of knowledge expansion the Wiki-on group shows *no improvement* (or worse, more errors) than Wiki-off on a blinded test set, we reject the hypothesis.  Concretely, we might decide: *“If human interventions per case do not decrease by ≥15% (or if failures do not drop) with the wiki, within 30 days, then the approach has failed.”*  Another rule: if a significant new error originating from wiki content occurs, that would cast doubt on the loop.  In other words, we should track both performance and any misstep and use them to reject or salvage the approach early.  

## 7. Consolidation of Knowledge Stores  

We already have **six** overlapping stores (wiki, boot-prompts, ticket notes, agent memory files, skills, vector memory).  Adding a seventh would be a mistake.  **Recommendation:** *Consolidate* rather than create new islands:

- *Unify front-end:* Build a single **retrieval façade**.  For instance, queries could first hit a combined index that knows to check the wiki, tickets, and skills in one go (e.g. using a graph of sources).  This is a routing problem (Mechanism B/C).  For example, it could weigh entity tags to decide which store (wiki vs evidence vs boot prompts) has likely info.  
- *Resolve overlaps:* Where content duplicates (e.g. boot-prompts vs wiki intro notes), choose one canonical source.  Our analysis found 944 tickets vs 482 wiki pages; many facts exist in both.  We should define “truth sources” by type (e.g. Git history for code facts, wiki for process, tickets for rationale) and prune duplicates.  
- *Federate indexes:* Use an embedding index that points to source pages across repos, not a new repo.  The wiki could remain primary for domain context, but the system should retrieve related ticket evidence seamlessly.  Tools like LlamaIndex or Chroma can index multiple directories.  
- *Tag alignment:* Leverage our existing frontmatter (tags on 64% of pages) to align content.  For example, if a ticket has a “sql” tag, the system might prioritize retrieving process docs on SQL from the wiki.  We should unify tag schemas across stores.  

No “silver bullet” from prior art says fusing multiple knowledge bases is easy; in fact the Context Engineering paper warns against five contexts everywhere.  It’s better to **reduce artifacts** than add.  So we do not recommend adding a new hierarchical graph DB or separate wiki layer now.  Instead, we should repurpose one of the existing stores as the central index (probably the wiki, since it’s largest) and consolidate others around it.  

Practically, the decision is: retire or merge at least one.  For example, boot-prompts are single-use documents that could be converted into skill templates (Mechanism E) or included in the wiki with a timestamp, then deleted.  Agent-memory files (one-fact files) could be batched into wiki pages (or a vector store used as ephemeral memory only).  The skills directory should become a known “skill library” (with README linking into the wiki) rather than living in both places.  

The key is: **one access layer**.  Agents should query “the knowledge system”, not a chain of imports.  We can achieve this by indexing all markdown into one vector DB with metadata (source type), or using a KG layer (like Graphiti) to unify them.  Given the evidence against adding silos, our first move is *consolidation*: repoint all retrieval to a single index that spans wiki+evidence+skills, then optionally add smart routing on top.  

## 8. Build Order (What to Do First)  

**Fix the pipeline first.**  Previous research rounds here have repeatedly flagged the control plane as broken (only 9/30 gates passing, 0 refusals on bad results).  We must not invest heavily in knowledge infrastructure until we have: sandboxing, cost metrics, and robust evaluation in place.  The gating logic must be fixed so that the system *will* block or alert on bad changes.  **Therefore, do NOT implement the auto-wiki loop or a new retrieval layer before:**  (a) building a fake-data sandbox to test changes harmlessly; (b) instrumentation on cost and retrieval success; (c) expanding our eval corpus from 1 case to ~30; (d) fixing the existing pipeline so it *can* refuse or require human review on clearly incorrect answers (e.g. add test-run rollback of database changes).  

Only once the pipeline reliably detects false deployments and the gate logic is known to work should we proceed to restructure knowledge.  Even then, we would start small: e.g. test structured context assembly on one agent vs none, or add a simple RAG phase and measure local effect, rather than fully auto-generating pages.  

If the final verdict is “no, don’t build,” our fallback should be **skill/knowledge distillation** rather than another wiki.  That means focusing on Mechanism E: manually crafting a library of key procedures and ensuring agents call them.  It also means improving search across what we have: for instance, enabling embedding search over the existing wiki and skills (possibly with Chromadb or Zep) so agents can find relevant info quickly without a fancy hierarchy.  In short, get better mileage from what *exists* rather than build new layers.  

## 9. Two-Week Decisive Experiment  

**Experiment:** Build a minimal “wiki-on vs wiki-off” test for one core task.  Pick a representative data-engineering scenario (e.g. modifying a data pipeline and verifying outputs).  Split a pool of ~30 test cases in half.  For the “wiki-on” half, enable retrieval from the current wiki (vector or keyword) and use its content in the agent’s prompt.  For “wiki-off”, the agent uses only prompts and code context.  Keep the agent code identical otherwise.  

**Measurement:** Predefine success metrics (e.g. number of human interventions required, or whether the final SQL/view is correct).  Establish a pass threshold: e.g. if Wiki-on reduces intervention count by ≥20% *or* increases correct outputs by ≥15% (p<0.05) compared to Wiki-off, consider it a meaningful benefit.  **Decision rule:** commit to the wiki plan if it shows a *statistically significant* improvement on these metrics.  If not, or if Wiki-on causes any new errors that Wiki-off avoids, we abandon the idea.  

Crucially, have a control for gating: ensure any knowledge retrieved from the wiki is clearly marked as “read-only reference” in logs, and have a human check all outputs for truth during the experiment.  Also monitor how often the agent *rediscovered* wiki facts vs actually used them, to gauge how much the wiki *really* helped.  This experiment isolates the effect of our knowledge base *before* adding complexity like hierarchy or auto-writing.  

**Decision rule (pre-set):** If after two weeks the wiki-supplemented agents show **no measurable improvement** (or worse, any hallucination that needed human fix) over baseline, we halt further investment.  If they show *clear gains*, we iterate: next, we might test adding structure or a small agent memory layer.
