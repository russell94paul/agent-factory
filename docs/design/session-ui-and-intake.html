Two rules fall out of that, and they should be load-bearing in any UI you build:

  • Liveness is metadata about how to answer, never a filter on whether to show. Attach, resume, or accept nobody is there — but the question renders either way.
  • Oldest first. Not newest, not grouped by session. The whole failure was old questions going unseen.

The layout

A control room, not a card grid. Three zones, because there are exactly three things you do: scan for what needs you, watch one thing closely, and act on it.

What to build first, and it is small: the left rail. The question inbox already exists in sessions.blocked() and is already correct. Rendering it as the primary surface — above the lane list, above everything — is a UI change with no new machinery behind it.

02

Vague request → hard spec

Already designed, as four tickets. The mechanism is better than "ask the client more questions", and worth stating plainly because it is the part that makes the output checkable.

One caution before you invest here. The claim that structured intake lifts spec completeness from 30–40% to 70–80% is basis-absent — it traces to an unsourced projection in a food-waste ontology feasibility study, a different domain. It is logged as D-4, still open. The intake critical path was prioritised on that number. The design is sound on its own merits; the priority is what rests on an unchecked figure.

03

The portal, and why auto-continue is not a portal feature

This is the finding. You asked whether the build could continue automatically once a client answers. The mechanism for that already exists — and the thing standing in its way is not the portal.

The portal itself is specified and its hardest prerequisite is already met:

TicketWhat it saysNote
CIP-11Portal renders the intake with per-field status, 5-term vocabulary same discipline as the session states — no collapsing
CIP-12Submit → PR → Jira. The portal mirrors and owns nothing. the key architectural call
CIP-13Reuse portal_provision.py auth + RLS; no new auth model exists aldc-launchpad/cli/

CIP-12 is the one to hold onto. A portal that owns state becomes a fourth ticket-record system, and three already disagree in this estate. Client answers land as a PR and a Jira update; the portal is a view. That also makes the automation question tractable, because an answer arriving is then just a commit.

The loop you are describing, drawn honestly

So the sequencing answers itself. Build the loop with a human at the resume step — that is SUPERVISED-OK today, and it is the only way to measure the loop at all. Make it automatic the moment ceiling, cap and reaper go green. The feature you want ships as a consequence of RUN-01/02, not as a separate build.

The one thing worth designing now that has no ticket

A client answer and an agent question are the same object seen from two ends, and nothing in the repo says so. JOBS/<id>/state.json holds needs; the portal will hold a per-field status in a five-term vocabulary. If those two are designed separately they will disagree — the same way the lanes and the tickets now describe one body of work in two vocabularies, and the same way three ticket-record systems already drift.

Design the question record once, with: who is being asked (agent / internal / client), what field it resolves, what check the answer unblocks, when it was asked, and — per R19 — what the agent was going to do either way. That is a spec you can write today without touching a file another session owns.

If you want to spend the wait well

  1. Write the question-record spec — the one gap above with no ticket, and the join between §1 and §3. New file, no collisions.
  2. Draft CIP-07's 20–30 questions against the four ontology dimensions. Blocked for building, not for drafting — and CIP-08 will force each one to earn a field and a check, so a rough list is genuinely useful input.
  3. Settle D-4 — put a basis label on the 70–80% figure, including its "how it dies" condition. It is currently deciding priority.
  4. Leave the layout unbuilt until the left rail is. The inbox is the only part with working machinery underneath; everything else in the wireframe needs RUN-03 first.
