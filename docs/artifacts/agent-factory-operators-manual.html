User guide

Everything here is a working command against the repository at 827f871. Start to finish is about ten minutes, most of it the browser download.

2.1 Standing it up

python -m venv .venv && . .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
python -m playwright install chromium          # the browser; pip cannot fetch it
pytest -q                                      # all four gates must pass
python -m factory.demo                         # end-to-end on a fake connector

scripts/bootstrap.sh runs all of the above.

Avoid — the browser step is a real step

pip install provides the Playwright driver and not a browser. Anything that validates a rendered page fails without it — and no client-facing artifact is certified without one. Check before you trust the environment:

python scripts/meeting_ready.py --check-env   # names everything missing, in one message

2.2 The two things worth doing first

python -m factory.certify blueprints/windsorai_client_a.yaml --calibrate
# connector-e2e/windsorai@CLIENT-A: PASS (PASS=12)

python -c "from factory import registry; [print(w) for w in registry.unproven()]"
# everything that is not certified — read this before believing anything
Avoid — reading that PASS as more than it says

It is a replay against one recorded connector. Not a live measurement, not a second subject. Every assertion has been proved able to fail (test_every_assertion_has_been_proved_able_to_fail) — but sensitivity is not coverage, and 48 connectors have never been scored.

2.3 The five verdicts — never collapsed

Borrowed from conformance testing (ISO/IEC 9646, carried into TTCN-3 as a monotone lattice) for the reason its docstring gives: collapsing “I could not look” into “I looked and it was fine” is how a measurement that never happened passes for one that did.

PASS
Asserted, and the assertion held. The only verdict that is a pass.
FAIL
Asserted, and the assertion did not hold. A real, trusted observation.
UNMEASURABLE
The instrument declined to run — it knows it cannot look. Not a pass. This is the important one.
ERROR
The apparatus itself broke. Not a measurement at all, and it dominates FAIL.
NOT_RUN
Never attempted. Distinct from every kind of attempt.

ERROR outranks FAIL because once the apparatus has broken, we no longer know the observed failure was real. A team holding an UNMEASURABLE is not certified.

2.4 Every figure carries a basis

For figuresMeansFor absencesMeans
MEASUREDObserved by a live instrument ZEROIt did not happen — and the instrument was live and could have seen it
DERIVEDComputed from measured values NOT-RECORDEDIt may have happened; nothing wrote it down
ASSUMEDTaken on faith; must be stated NOT-VISIBLEThe instrument cannot see this class of event at all
PROXYA stand-in for the real quantity NOT-RETAINEDIt was recorded and has since aged out
The rule that generates all four absence verdicts

A zero from an instrument you have not proved can still see is not a measurement. Before publishing “none / never / stopped / zero”, demonstrate the instrument would have registered a non-zero in that window.

03

AI Agent vs AI Operative

The design distinction the whole platform is built around — and the reason the word “operative” was borrowed rather than invented.

An agent is something you run. An operative is something you can certify, deploy, revoke and be accountable for.

AI Agent AI Operative
What it isA capable process. A model, a prompt, some tools, a loopA certified, versioned, mandated unit of work with an identity, an authority envelope, a measured capability record, and an expiry
IdentityA name someone chose. “The reviewer agent” A hash of its configuration. Change model, effort, prompt, tools, prohibition or target repo and it is a different operative
AuthorityWhatever its tools happen to permit An explicit mandate: what it may touch, what it must not do, which surface it may run on, what budget it holds, which decisions escalate
CompetenceAsserted in a description Measured, with conditions attached — task family, evidence count, success and regression history, cost, latency
TrustPermanent until someone notices otherwise Expiring. A capability record carries valid_until; a closed window cannot be reported as coverage
FailureReported as an error, or not at all Enters the lattice. “I could not look” is never a pass
OutputA result A result plus the evidence that closed it, plus what remained unmeasured
To the systemA caller A record — durable, addressable, auditable, and refusable

3.1 The seven properties

An agent becomes an operative when — and only when — it carries all seven. Remove any one and it is an agent again.

01
Designation
Identity is the configuration, not the label. version = sha256(config), so a silent upgrade cannot inherit a guarantee nobody re-checked.
02
Remit
Deadline, budget, authority and autonomy mode live in an ExecutionMandate — kept separate from the success contract.
03
Prohibition
An explicit “must not”, inside the hash. “Do not touch prod” in a prompt is a request; if deleting it changes the identity, it is a control.
04
Clearance
Execution surface and isolation tier, chosen from what the work declares, not from what is convenient.
05
Record
Competence with its conditions attached — corpus, tenants, surface, model binding — plus limits_unmeasured. DESIGNED
06
Expiry
valid_until. Winning placement can flip across model families, so trust decays. DESIGNED
07
Account
It cannot close its own work on its own word. factory/tasks.py raises EvidenceRequired; the grader is a separate identity.
Avoid — the allow-list bug, which happened here

The team hash originally enumerated four keys by hand, so repo and the team-level prohibition sat outside it. A team certified against one repository under “must not deploy to production” kept the identical version when repointed at another repo with the prohibition deleted.

Those are exactly the two edits that change blast radius. It is now a deny-list, not an allow-list: a new field is identity by default and must be argued out.

3.2 Operatives, not personalities

✗ A description — nothing can check it
conscientiousness: high
skepticism: medium
curiosity: high
✓ Compiled behaviour — each clause observable
pre_work_requirement_check: required
max_unresolved_assumptions: 2
post_change_validation: required
self_review_passes: 2

Archetype names — Scout, Surgeon, Architect, Skeptic, Auditor, Firefighter, Guardian, Integrator, Maintainer, Investigator — survive only as presets over measurable configuration deltas, and each must answer four questions before it is more than vocabulary. The fourth retires most of them: does it add anything beyond prompt wording?

Honest state of this section

Properties 1–4 and 7 are BUILT or PARTIAL and cite running code. Properties 5 and 6 are DESIGNED. With 0 PASS in the ledger there is nothing certified to describe. The operative model is the target the architecture is shaped toward, not a claim about today.

04

Daily use

What an operator actually does on a working day. Four loops, each ending in a verdict rather than an opinion.

4.1 Morning — read the board before touching anything

python -m factory.board                    # derived from gate verdicts, never hand-maintained
python -m factory.readiness --summary      # 30 gates across 5 phases

The board has no task list by design. It is derived from gate verdicts so it cannot drift from what it reports. A goal with no measurable gate reports NOT-MEASURED — not 0%.

Think about

Whether anything moved to UNMEASURABLE overnight. That is usually an instrument regression — a credential expired, a browser missing — not a product regression, and it is fixed somewhere completely different.

4.2 Starting work — the ticket must name a real target

python -m factory.certify blueprints/<target>.yaml --calibrate   # replay first, always
Avoid — inheriting the target from the ticket

An object named by a ticket, boot prompt or handoff is a hypothesis, not a finding. Walk the consumer route yourself and say which hop actually produces the symptom.

This cost a wrong-layer deploy and a revert once already: two objects held identical values and were still different objects. Never infer the source from matching values.

4.3 During — one command per verdict

Avoid — the chained check that reports on a check that never ran 
git rev-parse --short main personal/main && git merge-base --is-ancestor $B main \
  && echo "YES: merged" || echo "NO: merge needed"

The first command failed. Everything after && was skipped. The trailing || caught the chain’s exit status and printed NO: merge needed — for a branch that was fully merged, from a check that never executed.

Any command whose output carries a verdict runs on its own line, and you read its actual output. A chain’s exit status is not a measurement.

4.4 Closing — evidence, or it does not close

python -m factory.tasks close <id> --evidence docs/evidence/<set>/
# EvidenceRequired is raised by the store, not by a convention

The refusal lives in the store. An operative cannot close its own work on its own word, and the grader is a separate identity — a system that scores itself has measured nothing.

Think about

Whether the evidence proves the fix works at the layer the consumer reads. A DAX query can pass while every visual on the page shows an error — that has happened, and the query layer said everything was fine.

05

Business use

The commercial claim is narrow on purpose, and it is the one thing most agent platforms cannot say.

A team of agents did the work, and we can prove it — or we can prove we could not tell.

That second clause is the product. Most platforms can tell you an agent ran. This one tells you whether the thing that measured it could have registered a failure, and refuses the word “pass” when it could not. In regulated, client-facing or reconciliation work, the refusal is worth more than the throughput — because the cost of a confident wrong number is not the rerun, it is the client relationship.

5.1 Where it pays

SettingThe failure it prevents What the client is handed
Client data delivery A dashboard renders 0.00 where the truth is “not reported”. Absence arrives as a number and nobody can tell Figures carrying MEASURED / DERIVED, and absences carrying which of the four they are
Usage & billing audits A count from an instrument that could not see the window, published as “zero usage” A declared counting basis, an enumerated population, and a second independent instrument with the reconciliation shown
Multi-tenant reporting One client’s rows landing in another client’s table, invisibly A tenancy assertion that fails loudly — §07
Migration & repointing Parity passes at the query layer while every visual shows an error Before/after captures of the rendered surface, not just the query

5.2 What is deliberately absent, and what unlocks it

This table is a gate, not a wish list. Each row is cheap to add after its precondition and expensive to unwind before it.

Zero teams are certified. Every row above sits behind that. The most valuable next action in the entire programme is not on any roadmap: fix one open finding and complete one real run. That single measurement converts roughly a dozen research questions into observations.

06

Deep dive — certify one connector

The full path for connector-e2e/windsorai@CLIENT-A: six stages, each with what to think about and what has actually gone wrong here. This is a real sequence, so it is numbered.

01

Declare — write down what “green” means

A ConnectorTarget states every expectation before any observation: landing table, primary key, required accounts, date column, non-null columns, tenant column, allowed tenants.

primary_key: [account_id, campaign_id, date]
key_column:  account_id        # the column required_keys live in
tenant_column: account_id
non_null_positive: [spend]
Think about

Declare the requested scope, sourced from what the flow asks for — never from what landed. Reading the declaration out of landed rows makes completeness unfalsifiable: the test can then never fail.

Avoid

Guessing a class name from a naming convention. This file once declared WindsorAiConnection inferred from convention under the comment “Not yet read from source”. The real classes capitalise the initialism. The first live instrument caught it within seconds — a DERIVED value dressed as a declaration.

02

Preflight — prove the thing you are testing is the thing you shipped

Image digest, commit, and merged_at: the image must have been built after the merge. Without this, a green run can be a green run of last week’s code.

Think about

Whether the digest you compare against is the one the runtime actually pulled, or the one the registry says is latest. Those diverge exactly when it matters.

03

Canary — one run date, checked hard

Rows landed, primary key honoured, no null spend, every requested account present, date column in range. expect_rows: false exists for sources where an empty extraction is legitimate — an empty result is not automatically a failure, and the contract has to say which.

Avoid — the blind-instrument zero

A probe that cannot reach the warehouse returns nothing. So does a connector that landed nothing. These are different facts and must be different verdicts (UNMEASURABLE vs FAIL). The base Probes class refuses everything by default, because an unconfigured harness must report UNMEASURABLE and never PASS.

04

Tenancy — the assertion that protects the client relationship

Every landed row’s account_id must fall inside allowed_tenants. This is the one that stops CLIENT-B’s rows sitting in CLIENT-A’s table where nothing downstream can tell.

Why it exists — a measured fact

One shared vendor key returns every client’s accounts: 45 Google Ads accounts come back on an unfiltered pull, of which 6 belong to CLIENT-A. An unfiltered pull lands the other 39 clients’ rows in your table silently.

Avoid — a passing tenancy check that means nothing

The declared list was verified 2026-05-29, twelve weeks before the blueprint, and its own source file says “Confirm against a live pull before activation.” A PASS here means “the landing matched what we declared” — not “what we declared is still correct.” Those are different claims and only one of them is tested.

05

Certify — replay against a pinned corpus

python -m factory.certify blueprints/windsorai_client_a.yaml --calibrate
# connector-e2e/windsorai@CLIENT-A: PASS (PASS=12)
# scored against corpus windsorai-2026-08-20 — REPLAYED, not a live measurement
Avoid — treating calibration as evidence

certify.py says it about its own flag: --calibrate is “worthless as evidence that an agent did not grade itself.” It proves the instrument’s sensitivity. It does not prove the subject.

Think about — sensitivity is not coverage

Every assertion has been proved able to fail. The corpus is one file and 48 connectors have never been scored. The gap is breadth, not sensitivity — and those are fixed by completely different work.

06

Promote — the gate, and the rollback

Before any CREATE OR REPLACE or deploy, four things must exist together: the target proved by a discriminating test, correctness at the consumer’s layer, no-regression evidence, and a captured rollback.

Avoid — validating only at the layer you changed

A repoint once passed query-layer parity while every visual on the published report showed “Error loading data” from a stale dataset name. The consumer’s layer is the rendered surface a person sees, not the query that feeds it. Load the deployed surface, toggle every filter, and record which components respond and which are inert. A silent no-op is a finding, never an acceptable default.

07

Models across accounts

Manage, deploy, monitor and optimise model bindings across a multi-account estate — where the accounts belong to different clients and a single vendor key can see all of them.

The real topology, measured — read before scaling any of this

The estate does not currently hold twenty certified accounts. What is measured is: 6 Google Ads accounts declared for CLIENT-A out of 45 visible on an unfiltered key, and 3 Meta accounts authorised out of 19 visible — whose literal ids were never written down.

So of ~9 accounts in scope, 6 are declared and testable and 3 are NOT-RECORDED. The method below is what makes any N safe; the honest count today is 6.

7.1 The shape of the problem

The gap between 64 visible and 6 declared is the entire multi-account risk surface. Nothing downstream of the landing table can tell you which of those 64 a row came from — so the check has to happen at the boundary, and it has to be a declaration written in advance.

7.2 Manage — the account is a tenant, and the model is a binding

Two independent axes, and conflating them is the common mistake. An account is whose data it is. A model binding is what reasons over it. The same operative may run across six accounts on one binding; the same account may be served by three different bindings at different stages.

FieldAxis Consequence of changing it
allowed_tenantsAccount Widens or narrows what may legitimately land. Widening it silently is the multi-tenant leak.
modelBinding Changes the operative’s identity hash. Prior certification does not transfer
effortBinding Same — inside the hash. A silent effort bump is a new operative
budget_usdBinding Per-agent ceiling. The architect holds $5, the implementer $8, the tester $5
prohibitionBinding Inside the hash by design — deleting it produces a different operative, loudly

7.3 Deploy — bind the model to the role, and record why

The shipped team is three seats, each with a different binding chosen for the work, not for uniformity:

SeatModelEffortBudget Must not
architectopushigh $5.00write implementation code — a planner that implements is not planning
implementersonnetmedium $8.00mark its own work green — the tester holds the contract
testersonnethigh $5.00report PASS when an instrument could not run
Think about — a preset may not name a model without saying why

factory/presets.py enforces the shape: a preset that names a model must carry a model_why and an escalation trigger naming the condition under which that choice is wrong. Reasoning effort and model are properties of the task contract, not habits of the operator.

7.4 Monitor — what is actually recorded per run

The three lanes with MEASURED basis carry full token accounting. The numbers are worth looking at because they are dominated by something people rarely instrument:

The optimisation nobody looks for

Cache read dominates every other figure by two to three orders of magnitude. The control-plane lane read 454 million cached tokens against 1.47 million output. Optimising the prompt would move the small number; optimising what gets re-read moves the large one.

Note also the wall clock: artifact and control-plane ran ~30 hours each. Per-run cost is not the useful unit at this shape — per-lane cache behaviour is.

Avoid — averaging across bases

Three runs carry MEASURED; seven carry NOT-RECORDED with zeroed token fields. Averaging all ten produces a per-run cost that is 70% fabricated zeroes. Filter on basis before computing anything.

7.5 Optimise — and the gate that stops you

The optimisation loop is designed and deliberately unbuilt. The entry condition is not a preference:

OptimisationBlocked until
Model/effort routing per task class Observed outcome data. No routing rule may be written from intuition — capability classes, not model names
Correlated-failure-aware team composition Repeated comparable missions across task classes, conditions and seeds. One real run is a smoke test, not a covariance sample
Measured ablation of components Multiple comparable runs. ⭐ The protocol may be designed now and exercised on controlled benchmarks
Any per-run cost claim More than three MEASURED rows
Avoid — the failure this whole estate is organised against

A retired loop in this repository ran 965 times, measured its own 1.6% success rate, and never acted on it. Volume is not evidence, and a measurement nothing changes is indistinguishable from not measuring.

7.6 The operating rule, in one line

Declare the account scope before the pull, bind the model inside the identity hash, record the basis on every figure, and let the tenancy assertion fail loudly. Everything else in this section is a consequence of those four.
