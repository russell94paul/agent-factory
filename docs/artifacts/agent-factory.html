02 — the map

The system, in three planes

Build, data, serving. Pick a plane to drill into what actually moves through it, and which assertion watches each hop. Every arrow is labelled with the operation performed, not the relationship implied.

Build plane — what has to be true before a run is worth spending

Five assertions sit here, and all five are cheap. A canary run that fails because the image predates the merge proves nothing and costs a warehouse write.

The 2026-08-20 windsorai run passed all five — the image was checked to postdate the merge before a run was spent.

Data plane — where “the run finished” and “the work happened” come apart

The connector returns an empty dataframe on any non-200 response and raises nothing. So the flow run reaches COMPLETED with zero rows landed, and a run-state check calls that success. The lower path is that failure, drawn as the path it actually takes.

A6 passing while A7 fails is the shape of both historical failures in this estate.

Serving plane — two consumers, one much smaller than it looks

Power BI is not only the reporting layer; it sits inside Zeus Chat's read path. But the chat path reads 50 measures, not 306 — which is the difference between a migration and a rewrite.

No GreenContract exists for this plane yet. It is where a client notices, and it is unmeasured.
Read this before trusting the map

The serving plane carries no assertions. Everything in section 04 judges whether rows landed correctly — nothing yet judges whether the number a person reads is the number the warehouse holds. That gap is deliberate for team one, and it is the first candidate for team two.

03 — the precedent

How this failed twice already

Both mechanisms were capable. Neither was measurable. That distinction is the entire design premise of what follows.

A pipeline agent ran for 81 days. It produced 233 diagnoses and 234 escalations, and applied zero fixes. Separately, an automated loop ran 965 times, recorded its own success rate at 1.6%, and never adjusted. Neither was stopped by a monitor, because in both cases the thing being counted was activity — and activity was exactly what both were good at.

The sequencing objection, in the estate's own words

The original brief proposed roughly ten new subsystems — an army tier, a gym, an optimizer, five communication topologies, ten team types, a platform UI and a simulator. Six of them are downstream of one missing artifact: an eval. An optimizer is a search over configurations; a search needs a fitness function; the fitness function is the eval. Build the machine first and you have built a bigger version of the thing that already failed here twice.

04 — the instrument

The GreenContract

Twelve assertions. Every one states a positive fact that must be observed — none is satisfied by the absence of an error, because the runtime can fail totally and raise nothing.

The four verdicts are never collapsed. PASS was asserted and held. FAIL was asserted and did not hold. UNMEASURABLE means the instrument could not run — and it is not a pass. NOT_RUN was never attempted. Collapsing the third into the first is how a measurement that never happened passes for one that did; it is also, precisely, the live defect in the QA gate.

What the calibration found that review had not

On its first run the matrix passed a partial extraction — an entire account missing from the landing, and A9 reporting “18 rows satisfy every declared invariant”. The completeness check was guarded on a blueprint field the blueprint left empty, so it silently never ran. It was fixed structurally rather than by filling the list: the requested keys now come from the live config observation, and when nothing can supply them A9 reports UNMEASURABLE.

An invariant that quietly does not run is an assertion that quietly stopped being made — and from the outside it is indistinguishable from a pass.

05 — anatomy

An agent, a team, and what a version means

An agent is not a name. It is a tuple, and the tuple is the version — so a silent model upgrade cannot inherit a certification nobody re-checked.

The agent

Prompt, model, effort, tools, turn cap, dollar cap, and one explicit prohibition. The version id is a hash of that config. Change any element and it is a different agent whose certification does not transfer.

caps
every launch carries --max-turns and --max-budget-usd
prohibition
each agent states what it must not do, in its own config
version
sha256 of the config, first 12 — not a label someone types

The team

Two levels, one topology: manager to agent. A supervisor tier gets added when a second team exists and coordination between them is measurably the bottleneck — not before.

Every extra topology is a new seam, and every measured failure in this estate has been a seam failure: nobody owned “did the deploy finish?”, nobody owned “who reads this output?”

Deploying an agent to a repo is already solved here and does not need reinventing: a git worktree is created on a fresh branch, the agent is launched inside it with a turn cap and a dollar cap, stdout is streamed to a transcript, and the worktree is reclaimed afterwards. Elevated permission is granted only because the worktree isolates it. What is not solved is deploying a team — several agents against one change, with an ownership rule or a merge order. That is the narrow open question, and it is question 8 in the research brief.

06 — the only team

Team one: the data pipeline team

Scope decided: source → container → Prefect → warehouse. Power BI is out until a team has proved it can land rows.

The brief listed ten team types. This builds one. The estate's own analysis had already reduced seven crews to four and called two of those seats rather than crews; expanding to ten moves backwards from a conclusion already reached with evidence. One team, one contract, one connector proved end to end — then the second team is chosen by whatever the first one hurt.

07 — blast radius

Tenancy, the gate that does not exist

One vendor key returns every client's accounts. An agent fleet acting across GEP and Fusion92 without a tenancy check is one bad filter away from a cross-client leak.

This is not hypothetical here. A single ALDC Windsor key returns accounts belonging to every client on it, so a pull that omits the account filter lands another client's rows in this client's table — and nothing downstream can tell, because the rows are perfectly well-formed. They pass every other assertion in the contract.

The bound that must exist before any optimizer does

The measured incident was an uncapped watchdog re-dispatching a permanently failing stage every thirty minutes overnight, with its attempt counter living in an in-memory dict — so every restart handed it a fresh budget. Per-session caps already exist; the re-dispatch loop is what was unbounded. An optimizer that iterates until optimal with an in-memory counter is that incident with a larger bill.

Three rules travel with it: the eval lives outside the agent's writable tree, promotion is a human act, and the evaluator is a frozen versioned artifact the thing being evaluated cannot modify.
