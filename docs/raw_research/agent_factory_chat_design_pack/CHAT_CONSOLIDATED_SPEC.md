## Design requirement

Every metaphor must map to typed state.

Examples:

- “building on fire” → deployment or mission failure state.
- “broken supply line” → context, credential, environment, compute, or dependency unavailable.
- “fog” → unsupported/unknown/low-confidence information.
- “unit pinned” → agent/team blocked.
- “front line” → priority derived from objective/risk/dependency/value.
- “returning threat” → recurring failure family.

Never generate fake urgency or military drama with no operational meaning when the visual is used for actual work.

# 07 — Metrics, Failure Recurrence & Army Health

## Recurring Failure Rate (RFR)

Failure rate and recurring failure rate are different.

Basic definition:

`RFR = repeated failure occurrences / total failure occurrences`

RFR answers:
> How much of our failure volume comes from problems we have already encountered?

## Event model

Do not count retries as separate recurrences.

Hierarchy:
- Attempt Failure
- Incident
- Failure Fingerprint
- Failure Family
- Recurrence
- Previous Response
- Prevention Knowledge/Control
- Outcome

Example:
One mission retries the same failing operation three times = one incident with three failed attempts.

If the same root-cause family returns on later dates = recurrence.

## Failure fingerprint

Potential fields:
- failure_family
- subsystem
- component
- root_cause
- stage
- error_signature
- semantic_embedding/fingerprint
- affected_dependency
- prior_remediation

Do not rely on literal error-string equality.

## Recurrence metric suite

### 1. Recurring Failure Rate
Repeated failure occurrences / all failure occurrences.

### 2. Recurring Incident Count
Number of later incidents matching a previous failure family.

### 3. Failure Family Frequency
Occurrences by root cause family.

### 4. Time to Recurrence
Elapsed time from remediation/closure to next incident in same family.

### 5. Post-Fix Recurrence Rate
Failure families marked fixed that later recur / failure families marked fixed.

### 6. Preventable Recurrence Rate
Recurring incidents where sufficient preventive knowledge/control already existed / recurring incidents.

### 7. Doctrine Effectiveness
How often documented/encoded doctrine prevents or resolves the failure class.

### 8. Knowledge Reuse Rate
How often relevant prior experience is actually retrieved and used.

### 9. First-Pass Success
Mission succeeds without rework/retry/escalation.

### 10. Human Intervention Rate
How often a human must step into a mission.

## Organizational learning chain

For a recurring failure, inspect:

1. Did preventive knowledge exist?
2. Was it retrieved?
3. Was it delivered to the correct actor?
4. Was it understood?
5. Was the correct doctrine/action followed?
6. Did the doctrine actually work?

Failure classification:
- knowledge missing,
- retrieval failure,
- routing/communication failure,
- context compilation failure,
- execution/compliance failure,
- doctrine failure,
- structural prevention missing.

## Escalation by recurrence

Example policy:

Occurrence 2:
- retrieve prior incident,
- notify squad commander.

Occurrence 3:
- specialist reinforcement,
- mandatory root-cause analysis,
- escalate one org level.

Occurrence 4:
- doctrine review,
- Advanced Projects Command investigation.

Occurrence 5:
- war-game structural prevention,
- require validated systemic fix.

## Metric inheritance

Metrics should aggregate at every organization node.

Example:
- OAuth Squad RFR: 42%
- Authentication Company: 31%
- API Battalion: 17%
- Connector Division: 11%
- Integration Corps: 8%
- Engineering Command: 6%

This makes recurrence hotspots visible spatially.

## Suggested top-level Army Health scorecard

- Mission Success Rate
- First-Pass Success
- Recurring Failure Rate
- Preventable Recurrence Rate
- Time-to-Green
- Cost per Accepted Outcome
- Human Intervention Rate
- Rework Rate
- Knowledge Reuse Rate
- Doctrine Effectiveness
- Readiness
- Evaluation Pass Rate
- Gate Rejection Rate
- Outcome Regression Rate

# 09 — 10 Business-Value-First Concepts

## 1. Surveillance / Satellite Mode
Show only incidents, blockers, queues, abnormal spend, uncertainty, unanswered distress, and approvals.

Replaces:
multiple status/alert/approval dashboards.

Business hypothesis:
reduce time-to-understand and operator attention cost.

## 2. Reinforcement Router
Find the best available human/agent/team based on expertise, prior similar missions, availability, cost, and permissions.

Replaces:
manual directory search + Slack “who knows X?” + context handoff.

Business hypothesis:
reduce blocker duration and coordination overhead.

## 3. Collision Control
Detect duplicate work, overlapping file changes, contradictory assumptions, or scarce-resource conflict.

Replaces:
late merge-conflict discovery and duplicate investigation.

Business hypothesis:
reduce wasted agent cost and rework.

## 4. Command Authorization
Unified governed approval surface for consequential actions.

Replaces:
scattered approvals across GitHub, workflows, chat, deployment tools.

Business hypothesis:
reduce approval latency while improving auditability.

## 5. Frontline Optimizer
Prioritize missions against explicit Commander's Intent, dependencies, risk, urgency, and business value.

Replaces:
priority labels, roadmap sorting, repeated reprioritization meetings.

Business hypothesis:
increase value delivered per unit time.

## 6. Logistics Health
Continuously assess whether a mission has required context, credentials, tools, compute, environment, dependencies, and budget.

Replaces:
manual preflight and multiple diagnostic pages.

Business hypothesis:
increase first-pass mission success and reduce avoidable runtime failure.

## 7. After-Action Learning
Automatically structure outcome, successful tactics, failures, reusable lessons, new threats, and candidate doctrine.

Replaces:
manual retro/postmortem/knowledge capture.

Business hypothesis:
increase knowledge reuse and reduce recurrence.

## 8. Workflow Compression
Mine repeated stable agent/tool sequences and turn them into deterministic skills/meta-tools.

Replaces:
repeated expensive reasoning.

Business hypothesis:
reduce tokens, latency, variance, and failure surface.

## 9. Advanced Projects Command
Continuously discover and validate the highest-leverage organizational/product/process improvements.

Replaces:
fragmented innovation backlog and ad-hoc R&D.

Business hypothesis:
improve rate of validated high-value change.

## 10. Objective Ledger / Commander's Intent
Connect each operation to explicit success criteria and show actual contribution.

Replaces:
disconnected OKRs, roadmaps, project status, and engineering activity metrics.

Business hypothesis:
reduce activity optimization and improve outcome alignment.

## Graduation rule

A world interaction should generally graduate only if it:
- materially improves task completion speed,
- reduces context/navigation switches,
- reduces missed risks/errors,
- improves situation awareness,
- or enables a capability that is difficult in conventional UI.

The world does not need to win code editing, long logs, SQL, giant tables, or exact configuration.
